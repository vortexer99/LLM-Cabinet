## T1：库一致性检查

### 入口

「设置 → 项目库」加按钮 **🔍 检查库一致性**。

### 执行流程

1. 用户点击 → 弹进度对话框（按文件计数）
2. 后台扫描：
   - 取出所有 `is_relative=True` 的 `FileItem`
   - 对每个 `library.resolve(file.path, True)` 检查物理是否存在
   - 同时统计 `is_relative=False` 的链接文件中"原路径已失效"的（顺手做，不强求）
3. 完成后弹报告对话框：

```
┌────────────────────────────────────────────────┐
│ 库一致性检查报告                                │
│                                                │
│ ✅ 仓储文件（library/）：完整 248 / 248         │
│ ⚠️ 链接文件（外部路径）：失效 3 / 8             │
│                                                │
│ 失效文件清单：                                  │
│ ┌────────────────────────────────────────────┐ │
│ │ 项目         │ 文件名      │ 原始路径      │ │
│ │ 项目A        │ ch1.pdf     │ D:\...\ch1   │ │
│ │ 项目B        │ note.md     │ E:\...\note  │ │
│ │ 项目B        │ photo.jpg   │ F:\...\photo │ │
│ └────────────────────────────────────────────┘ │
│                                                │
│ 处理：[● 仅查看  ○ 标记为缺失  ○ 从项目移除]    │
│                                                │
│            [ 取消 ]   [ 应用 ]                  │
└────────────────────────────────────────────────┘
```

### 处理选项

| 选项 | 行为 |
|---|---|
| 仅查看 | 不动数据，关闭对话框；报告写到 `app_data_dir()/last-consistency-report.json` 留档 |
| 标记为缺失 | 给文件加一个 `missing` 标记（schema 加列：`files.missing INTEGER NOT NULL DEFAULT 0`）；UI 文件表显示一个 ⚠ 图标 |
| 从项目移除 | 调用 `repo.delete_file(fid)` 真删；不动磁盘上**别处**的文件；保留在 audit log（如 task #13 落地后） |

### Schema 变更

如果选"标记为缺失"路径，需要 schema vN → vN+1：

```sql
ALTER TABLE files ADD COLUMN missing INTEGER NOT NULL DEFAULT 0;
```

如果不做"标记为缺失"功能，T1 不需要 schema 变更。**取舍**：选"标记"更友好（用户能看到哪些丢了但不主动删），但代价是 schema 升级。建议**做**——schema 升级走 #08 / 现有迁移机制即可，成本低。

- [ ] 故意把链接模式文件的原路径改成不存在 → 报告里出现该文件

## T2：库备份 / 恢复

### 入口

「设置 → 项目库」加两个按钮：

- **📦 备份此库...** → `QFileDialog.getSaveFileName` 选 zip 路径 → 执行
- **📥 从备份恢复...** → 选 zip → 走"新建库 + 解压"流程（实质是 #08 新建库的扩展）

也在「库」菜单里挂一份入口（用户更可能想到这里找）。

### 备份流程

1. 关闭 LLM worker
2. **闪存 db**：`PRAGMA wal_checkpoint(FULL)` 保证 WAL 内容写入主 db
3. 用户在选择 zip 输出位置时若已有同名 → 沿用 #09 的 `unique_name` 自动加 `(2)`
4. 后台线程跑 `shutil.make_archive` 打包整个库目录
5. 进度条按 zip 写入字节数粗粒度刷新
6. 重启 LLM worker

### 恢复流程

1. 选 zip → 选目标解压位置（默认 `~/CabinetLibs/<zip 文件名 stem>`）
2. 如果目标目录非空 → 拒绝（不自动覆盖）
3. 后台解压
4. 校验解压后是否含 `cabinet.db` + `library/`，否则报错"这不是有效的 LLM Cabinet 库备份"
5. 把新位置当作"新建库"加入 cabinet.json，**重启切换过去**（沿用 #08 切换流程）

### 验收（T2）

- [ ] 备份后 zip 文件含 `cabinet.db` / `library/` / `.llm-cabinet`
- [ ] 备份过程中应用 UI 不卡死（后台线程 + 进度条）
- [ ] 备份完成后 LLM worker 正常恢复
- [ ] 大库（GB 级）备份不 OOM
- [ ] 恢复后切换到新库，项目列表与原库一致
- [ ] 恢复时选了非空目录 → 弹错误对话框，不破坏用户文件
- [ ] zip 不是有效库备份 → 弹错误，不创建残留目录

## T3：库搬家指引（文档）

不写代码。在 `README.md` / `README.zh-CN.md` 加一节，或单独写 `docs/library-management.md`：

> **想把库目录搬到 D 盘 / 网盘 / 移动硬盘？**
>
> 因为 LLM Cabinet 把每个库设计成"一个完整的目录"，搬家不需要导出/导入：
>
> 1. 关闭 LLM Cabinet
> 2. 在文件管理器里**整体剪切**库目录到新位置
> 3. 重新打开 LLM Cabinet，菜单 「库 → 切换库」选新位置即可
>
> 跨设备同步同理：把整个目录放到 OneDrive / Dropbox 等，**确保同一时刻只有一个客户端打开它**（避免 SQLite 锁冲突）。

## 风险

- **T1 大库性能**：10000+ 文件的扫描可能慢；用 `Path.exists()` 而非 stat，足够快
- **T1 标记为缺失的字段**：增加 schema 复杂度；如果用户从不跑一致性检查，列就一直是 0；但成本极低，可接受
- **T2 zip 体积上限**：标准库 zipfile 支持 zip64，无 4GB 限制；但整库可能 GB 级，备份慢，要进度条
- **T2 与 OneDrive 配合**：用户备份到 OneDrive 路径时 OneDrive 自己可能在同步那个 zip → 完成后 ms 级写入冲突。文档提示
- **T3 文档不维护就过期**：把"搬家指引"放进 README 末尾的"FAQ"区，未来重构时容易顺手更新
