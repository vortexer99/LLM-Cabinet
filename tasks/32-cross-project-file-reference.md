# 32 · 跨项目链接引用（最小方案）

**工作量**：S+S
**优先级**：P2
**状态**：待做

## 来源

`docs/file-handling.md` 评审时浮现的真实需求：用户希望同一物理文件能被多个项目共享（典型场景：同一本 PDF 既属于"原版收藏"项目，又属于"翻译对照"项目）。

设计取舍上有两条路：

1. **路径共享（本卡选）**：每个项目维护独立 `files` 行，多行 `path` 字符串相等。零 schema 改动；改 label / subfolder / ord / origin 各自独立。删除时靠"多引用警告"兜底。
2. **引用语义（远期）**：引入主 file 行 + N 条引用，删除主行需级联或拒绝。改动大，要重新设计 `cover_file_id` / `origin` / `subfolder` / `missing` 的归属语义。

本卡走 1。承担"库自包含被破坏"的代价（项目 A 删了 → B 失效），用删除时弹警告兜底。1 落地后再观察真实痛点决定要不要升级到 2。

- 可多选
- "目标子文件夹"下拉列出当前项目已有 subfolder + "顶层" + "新建…"

### 执行流程（每个文件）

1. `abs_src = library.resolve(src_file.path, src_file.is_relative)`（拿源文件的绝对路径）
2. 在当前项目（B）新建一条 `FileItem`：
   - `path=str(abs_src)`, `is_relative=False`（**总是链接模式**，不复制）
   - `label=src_file.label`（保留原 label，用户可后续改）
   - `kind=src_file.kind`
   - `subfolder=用户选的目标 subfolder`
   - `origin='user'`（**不继承源 origin**，理由见下）
   - `ord` 给 10000 走默认追加
3. `repo.add_file(new_file)`
4. 进度回调 + 完成反馈

### 设计决策

- **不复制，必链接**：跨项目共享的整个意义就是"共享同一份物理文件"，复制会破坏这个语义。如果用户想"独立副本"，用 #29 T1 链接转仓储。
- **`origin` 不继承**：源文件可能是 `generated`（如 A 的封面快照），但被 B 引用后对 B 来说是"用户主动引入的"，应该归 `user`。如果保留 `generated`，B 项目的"仅显示用户文件"筛选（#04）会把它隐藏，用户找不到自己引用的东西。
- **label 继承**：起码给用户一个起点，省得每次都得手动填。
- **不建立"引用关系"DB 记录**：本卡选择不引入新表/新列，"多引用"靠运行时查询 `WHERE path=?` 得出。代价是删除时要扫一遍 files 表，但 files 表行数远小于"每次扫描都不可接受"的量级。

## T2 · 多引用警告 + 一致性检查升级

### 触发场景

| 场景 | 处理 |
|------|------|
| **删除单文件**（`action_delete_files`） | 删除前扫 `SELECT project_id FROM files WHERE path=? AND id<>?`；若有其他项目引用 → 弹警告（见下） |
| **删除项目**（`action_delete_project`） | 删除前扫该项目所有 file 的 path，找出"被其他项目引用"的项 → 弹警告 |
| **#29 T2 移动文件到新位置** | 移动前同样扫多引用；若有，警告"其他项目也指向该文件，移动后这些项目的链接会失效"，二选一：取消 / 继续并打 missing 标记 |
| **#29 T1 链接转仓储** | 该文件是链接 → 转仓储后**只动当前项目的行**（path 改成库内相对路径）；其他项目仍指向原外部路径——不需要警告，但反馈对话框追加一行"其他项目仍引用原文件"提示 |

### 警告对话框

```
┌─────────────────────────────────────────────────┐
│ ⚠️  此文件被多个项目引用                        │
│                                                 │
│ 文件：D:\Books\foo.pdf                          │
│                                                 │
│ 当前要删除的引用（项目 B）：                    │
│ - foo.pdf                                       │
│                                                 │
│ 其他项目仍引用此文件：                          │
│ - 项目 A (foo.pdf)                              │
│ - 项目 C (中文版)                               │
│                                                 │
│ 删除这条引用不会影响物理文件、也不会影响其他    │
│ 项目。                                          │
│                                                 │
│              [ 取消 ]  [ 仍然删除 ]              │
└─────────────────────────────────────────────────┘
```

- **删除单文件 / 项目**：物理文件不动，只是本项目少了一个引用，所以警告语气是"提示"而非"拦截"。
- **移动文件**：另当别论——移动会让其他项目的 `path` 失效，这是真问题。警告升级，二选一：取消 / 继续（其他项目会被打 `missing=1`）。

### `repository.py` 新增辅助方法

```python
def find_references(self, path: str, exclude_file_id: int | None = None) -> list[tuple[int, int, str]]:
    """查找所有引用同一物理路径的 files 行。

    返回 [(file_id, project_id, label), ...]。不区分 is_relative——
    跨项目引用只可能是 is_relative=False（库内副本被引用必然是绝对路径）。
    用于删除/移动/转仓储前的多引用检测。

    Windows 平台对 path 应用 normcase 归一化（小写化 + 反斜杠转换），
    避免 `D:\\Books\\foo.pdf` 与 `d:/books/foo.pdf` 被判成不同文件。
    实现：内存归一化 + 表扫描后比较，不改 path 实际存储值。
    """
    import os
    norm = os.path.normcase(path)
    sql = "SELECT id, project_id, path, label FROM files"
    params: list = []
    if exclude_file_id is not None:
        sql += " WHERE id<>?"
        params.append(exclude_file_id)
    rows = self.conn.execute(sql, params).fetchall()
    return [
        (r["id"], r["project_id"], r["label"] or "")
        for r in rows
        if os.path.normcase(r["path"]) == norm
    ]
```

## 实现要点

### A. 不引入新表 / 新列

所有功能基于现有 `files` 表 + `path` 列字符串匹配。代价是 `find_references` 是 O(N) 表扫描，但 files 表行数级别（万级）下完全可接受；如真成瓶颈，加 `CREATE INDEX idx_files_path ON files(path)` 即可（schema 已开 v8 之后随时可加）。

> ⚠️ Windows path normcase：表扫描后内存归一化比较的代价是查询不能直接走 `WHERE path=?` 索引。如果加索引，应同时存归一化后的 `path_norm` 列（schema 改动）。**默认决定先不加索引，等真出瓶颈再说。**

### B. UI 集成点

- 文件表右键菜单（`main_window` 已有框架）：加 "🔗 引用其他项目的文件…"
- `action_delete_files`（`main_window.py:2620`）：调用 `find_references` → 有引用则弹警告
- `action_delete_project`（`main_window.py:2160`）：循环该项目 files 调用 `find_references`，汇总后弹警告
- #29 的执行流程里也插入同样的检查

### C. 与 #28 导出的交互

跨项目引用对导出意味着什么需要先想清楚（不在本卡实现，但要在卡里明确预期）：

- 项目 B 导出独立包时，被引用的文件物理在项目 A 库内 → 复制到 B 的导出包是合理选择（独立包嘛）
- 导入到新库时，新库里没有"项目 A 的库内文件" → 那条引用直接退化为独立 `files` 行（指向导入包里的副本），不再是"跨项目引用"
- 这与 #28 现有"copy_link_files" 选项语义一致；本卡完成后给 #28 加一行验收"被引用的库内文件在导出时按 copy_link_files 决定是否复制"

## 校验

### T1 跨项目引用
- [ ] 项目 B 右键 → 引用项目 A 的文件 → B 文件表出现该文件，存储方式列显示 🔗
- [ ] 双击该 file → 能正确打开（验证 `library.resolve` 拿到正确绝对路径）
- [ ] 引用的是 📦 仓储文件（A 库内）：在 B 看到的 path 是 `<lib_root>/project_A/foo.pdf` 绝对路径
- [ ] 引用的是 🔗 链接文件（A 外部）：在 B 看到的 path 与 A 完全相同
- [ ] 改 B 引用行的 label → A 不受影响（独立元数据）
- [ ] 引用时选目标 subfolder → 在 B 出现在正确分组
- [ ] 同一文件可被同一项目多次引用（label 不同）—— 允许，不去重

### T2 多引用警告
- [ ] 删除 B 的引用行 → 弹警告列出 A 仍引用 → 选"仍然删除" → B 少一行，A 不变
- [ ] 删除 A 项目 → 弹警告列出 B 也引用了 A 的文件 → 选"仍然删除" → A 没了，B 的引用行 `path` 仍指向库内旧路径（物理文件已随 A 删除消失） → 下次 #14 检查报告失效
- [ ] #29 T2 移动 A 的链接文件 → 弹警告 → 选"继续" → B 引用行被打 `missing=1`
- [ ] #29 T1 把 A 的链接文件转仓储 → 反馈对话框追加"其他项目仍引用原外部路径"
- [ ] 没有跨项目引用时 → 不弹警告，行为与原来一致

### T3 #14 一致性检查升级
- [ ] 报告对话框新增"跨项目引用：X 个物理文件被 Y 个项目引用"
- [ ] 点"查看清单" → 列出每个被共享的物理文件 + 引用它的项目列表
